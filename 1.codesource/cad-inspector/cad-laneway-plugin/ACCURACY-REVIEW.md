# 精度核对报告：插件输出 vs 云 CAD 导出数据

对比对象
- 参考真值：`导出巷道数据.json`（MAS Cloud CAD 导出，98 条巷道，总长 29,974 m）
- 插件输出：`银二井上下对照图.dwg` 识别结果（136 条，总长 33,724 m）

## 一、结果

| 指标 | 数值 |
| --- | --- |
| 巷道条数 | 真值 98 / 我方 136 |
| 总长度 | 真值 29,974 m / 我方 33,724 m |
| 中点距离 ≤ 2 m | **0 条** |
| 中点距离 ≤ 10 m | **6 条**（6%） |
| 中点距离 ≤ 50 m | 36 条（37%） |
| 中点距离 ≤ 200 m | 80 条（82%） |
| 系统性平移 | dx≈7 m、dy≈14 m（可忽略）；补偿后反而更差 |

## 二、结论

1. **不是坐标偏移问题**：整体只差 7/14 米，补偿后匹配数反而下降，说明两边不是"整体挪了一下"，而是**走的是不同的路径**。
2. **总量接近是巧合**：33.7 km vs 30 km 看着差不多，但逐条对不上——只有 6 条能在 10 m 内对上。
3. 我方 136 条里，大部分是"线划配对/单线推断"出来的，真值 98 条来自采集系统的对象（DWG 里是 98 个 ACAD_PROXY_ENTITY，与 JSON 条数一一对应）。

## 三、根因

人工图不是"照着 DWG 描线"得到的，而是 **MAS Cloud CAD 用采集数据（中线+宽度+点位+标高）渲染出来的对象**。DWG 里那 98 个代理对象就是这 98 条巷道的容器。

我们做的是"从线划反推巷道"：
- 双线配得上 → 取中线；
- 配不上 → 单线推断；
- 断点 → 按容差续接。

这三步都会引入与真值不同的路径，**条数、起止点、分叉位置**天然对不上，所以逐条比对只有 6% 命中。

## 四、可选的三条路

| 方案 | 做法 | 预期精度 | 代价 |
| --- | --- | --- | --- |
| A. 采集数据导入 | 插件只输出"中线+宽度+点位+标高"，导入 MAS 生成对象 | 与人工图一致（同源） | 需确认 MAS 的导入格式 |
| B. 真值校准 | 用 `导出巷道数据.json` 做模板匹配，把识别结果吸附到真值附近 | 中（能修偏移/断点，改不了拓扑） | 每张图都要一份真值，不现实 |
| C. 继续调参 | 调配对/续接/阈值 | 低（已验证 6%） | 已证明收益很小 |

建议走 A：把插件定位成"采集数据生成器"，而不是"CAD 描图器"。


## 五、真值数据模型（2026-11-16 补充）

`导出巷道数据.json` 是 **GBK 编码**（不是 UTF-8），单条巷道结构：

| 字段 | 实测值 | 含义 |
| --- | --- | --- |
| `border_line_points` | **3 段**（5 点 / 2 点 / 6 点） | 帮线按节点拆段，不是整条两条线 |
| `traverse_point_array` | 6 个点 | 每点含 `point_name`(H11)、`traverse_point_type`(导线点)、`z_top`/`z_bottom`、`left_side`/`right_side`(2.0) |
| `laneway_width` | 4.0 | = left_side + right_side |
| 坐标系 | 36388408 / 4169068 | 与图纸 WCS 一致，无偏移 |

**关键结论**：MAS 的巷道是"**导线点串成的路径 + 每个点左右半宽**"，帮线由系统按半宽生成。所以插件要产出的不是"两条线"，而是**沿导线点的中心线 + 半宽**。

我们已有的 JSON 字段与之兼容（25 字段一致），3.11.0 起导出改为 **纯 ASCII 转义**（`\u8f68\u9053`），对方按 GBK 读也不会乱码。

几何精度仍是 6%，下一步应按"导线点建图"重做中心线：图上半径 0.4/0.75 的圆圈就是导线点，用它做节点连边，正好对应真值模型。


## 六、4.0.0 实测（导线点吸附后）

| 指标（按真值点的最近线距离） | 结果 |
| --- | --- |
| ≤ 2 m | 10 / 98 |
| ≤ 5 m | 14 / 98 |
| ≤ 10 m | **18 / 98（18%）** |
| ≤ 20 m | 24 / 98 |
| 中位距离 | 59 m |

单图层试验（各自单独跑）：`巷道` 中位 32 km、`采区巷道` 32 km、`00中心线` 847 m，只有全部图层合起来才落在同一区域（59 m）——说明巷道线划分散在多个图层，且与真值路径仍不一致。

结论：吸附导线点只是把顶点拉回测量点，**没有改变"走哪条线"这个根本问题**；要达标还需要知道"巷道所在的线划"到底是哪些（图层/颜色/线型），或直接获得 MAS 的采集规则。


## 七、从真值 JSON 反推的“采集规则”（98 条统计）

| 项 | 规律 |
| --- | --- |
| 巷道宽度 | **全部 4.0 m**（98/98） |
| 巷道高度 | **全部 3.0 m**（98/98） |
| 左右半宽 | **2.0 m**（644/646 个点），偶有 3.0（2 个点） |
| 每巷道点数 | 2 ~ 34，中位 3，合计 646 点 |
| 点位类型 | **导线点 624**、**停头 22** |
| 点间距 | 中位 **41.3 m**、均值 54.7 m、最大 366 m |
| 帮线段数 | 2 ~ 47 段（随点位数增加，按点分段） |
| 坐标系 | 图纸 WCS，无偏移 |

推论：MAS 的采集是“沿导线点每隔约 40 m 取一点，宽度固定 4 m，帮线按相邻点分段生成”。插件已按此把点位间距默认改为 **40 m**。


## 八、MAS 采集接口（已找到，可直接写入）

Swagger：`http://192.168.100.54:61012/swagger/mas.xayl.WebCad.Controller/swagger.json`（470 个接口）

| 接口 | 用途 |
| --- | --- |
| `POST /XAYL_Designer/CADCollection/GisLaneway/CreateList` | **批量新增巷道**（主用） |
| `/GisLaneway/Create` `ModifyOne` `ModifyList` `Delete` `DeleteList` `GetList` | 单条增改删查 |
| `/GisLaneway/GetLanewayCenterLineList` / `GetLanewayPointCoordinate` / `GetLanewayBorderLinePoints` | 取中线、点位、帮线 |
| `/XAYL_WebCad/GisWebcadMapLaneway/SaveForm` | 图面级巷道保存 |

请求体：`{ "data": [ LanewayAddInfo, ... ] }`，`LanewayAddInfo` 有 **33 个字段**，与我们导出的 JSON 同名同义：`laneway_name / laneway_code / laneway_width / laneway_height / border_line_points / traverse_point_array / laneway_type / color …`

鉴权：Header `token: <JWT>`（与浏览器请求头一致）。

→ 结论：**不需要 DWG 描线，也不需要 JSON 文件导入**，插件直接把识别的巷道 POST 进去，由 MAS 生成 `MmDbLaneway`。
