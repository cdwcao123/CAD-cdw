## 二、用户最终需求与约束

1. 上传 DWG/DXF；DWG 转换为 DXF，DXF 直接解析；使用客户端设置中的默认大模型辅助采集。
2. 导线点由编号、空心圆、标高组成：编号、圆、标高相互靠近但排列方向不固定；圆可能是普通圆实体或块内对象，标高可能带字母后缀。部分点缺少标高时仍可作为候选。
3. 巷道是有序、有坐标的导线点序列，而不是相同标高或相同编号的点的集合。仅对应两条边线之间的圆心才可纳入该候选巷道，沿巷道走向排序；复杂交叉或扎堆区域可以保守跳过。
4. 缺失标高只依据同一候选巷道中两侧的实测标高点合理插值，区分实测与估算；无可靠锚点不外推。未知的顶板、底板含义不能凭空赋值。
5. 最终只输出一份 JSON，结构参考测试图纸文件夹的真实巷道 JSON；允许缺少字段，不虚构数据。真实 SDK 导入兼容性仍须验证。
6. 不擅自修改客户端。日志须脱敏：不要记录图纸文字、坐标、模型原文、凭证或完整异常。

## 三、已实现内容

- `manifest.json`、`index.js`、`worker.js` 版本为 5.4.0；前端只下载一份巷道候选数组 JSON。
- `server.js` 调用宿主 `ctx.engine.generate(request, ...)`，不显式指定模型，以使用当前默认模型。模型从已有实体 ID 中选择圆、编号和可选标高；本地校验选择合法性，最多三次尝试。对重试后仍部分无效的数组保留逐项可验证的选择、跳过不确定项；无法解析或网关异常不伪装为成功。
- `core/survey.js` 提取圆和文字候选，支持部分块展开、无标高点及标高状态；仍存在圆半径、邻近距离、候选文字数量等启发式限制，不能理解为用户确认的米制规则。
- `core/lanes.js` 基于两条边线形成区域，要求点严格位于内部；支持同层碎片双向拼接、不同合格图层之间的边线配对，并对密集、共享点或竞争边线的歧义候选保守跳过。同一候选内只在两侧实测锚点之间插值。`z_top`、`z_bottom` 保留为空。
- 前端 HTTP 异常使用固定安全提示，不直接显示请求异常原文；脱敏回归有覆盖。
- 图纸候选文字、位置等会发送给客户端默认模型，界面提示用户确认数据处理权限。

- 对拍把人工真值点直接输入建巷算法，按精确 XY、无向去重相邻边比较：5.4.0 输出 21 条候选巷道、49 条候选边，其中 43 条匹配 548 条真值边，召回约 7.85%，候选边匹配比例约 87.8%。
- 该结果仅衡量给定真值点后的连接，不衡量模型自动采点、点的标高准确性或整条巷道归属；人工真值可能不完整，未匹配候选边不必然是错误。对拍显示仍存在显著漏采，不能用作生产准确率。
- 5.3.1 同口径为 15 条候选、25 条候选边中 24 条匹配，真值边召回约 4.38%。5.4.0 覆盖提高，但候选边匹配比例下降，需重点核查误连风险。
- 旧 `tests/elevation-regression.mjs` 引用已移除的 `/review`；旧 `tests/schema-check.mjs` 与当前格式及真实参考不一致，不能据此宣称全部测试通过或 SDK 兼容。

## 五、接手优先级与完成标准

### 1. 真实客户端大模型故障

1. 先确认用户是否安装 5.4.0 并再次复现；检查 `C:/Users/admin/.local/share/elvespuck/data/plugins.json`、`C:/Users/admin/.local/share/elvespuck/logs/elvespuck.log`、`C:/Users/admin/.local/share/elvespuck/logs/plugins/cad-inspector.log` 的最新时间线。不要将旧日志误判为新版结果。
2. 按批次、请求 ID、错误分类和重试次数定位；若仍是 `point_name`，在不记录图纸原文、坐标、模型回复及秘密的前提下补充必要诊断，并以代表性样本复现校验失败。
3. 验证默认模型确实收到请求、能返回可验证证据，失败时界面和日志正确报告；勿用纯规则结果冒充模型采集。真实客户端未复测时必须如实标注。

### 2. 提高双边线建巷质量

1. 从真实对拍漏采和未匹配候选中抽样，分别确认碎片端点、图层过滤、边线配对、交叉密集区域及点排序问题，再增加合成回归和真实对拍。
2. 特别审查跨图层错配、分支截断、非平行或弯曲边界、边界上的点和共享点；每次同时报告召回与候选边匹配比例，不能只追求数量。
3. 验证块内圆与边线在同一坐标系；`core/parse.js` 与 `core/survey.js` 的块展开实现不同，复杂嵌套和非等比缩放仍可能漏检或错位。
4. 无标高点只在两侧实测锚点可靠且属于同一无歧义巷道时插值；增加测试验证估算标记、不外推及不虚构顶底板。

### 3. 输出格式和运行生命周期

1. 对比真实 JSON 字段及 SDK 导入行为，明确新增 `elevation`、`elevation_status` 等字段是否被接受；参考 JSON 的 `border_line_points` 并不总是固定两组。以实际 SDK 测试作为兼容结论。
2. 关于切页后台续跑，已知普通 full-page 页面卸载会终止 Worker、释放页面 HTTP，宿主 `ctx.engine.generate` 需要当前有效请求，不能缓存请求构造后台任务。先向用户说明需宿主提供的后台能力并取得修改客户端许可；不得把断点恢复描述为后台续跑。
3. 完成代码后运行上述回归、真实对拍、真实客户端模型测试与 SDK 验证；同步三个版本号，打新版本包并验证清单、完整性，不覆盖旧包。

## 六、代码和数据位置

- `cad-laneway-plugin/index.js`：界面、批量模型请求、模块内存断点和单 JSON 导出。
- `cad-laneway-plugin/server.js`：默认模型调用、重试、证据校验和脱敏日志。
- `cad-laneway-plugin/worker.js`：图纸解析、候选与结果组装。
- `cad-laneway-plugin/core/survey.js`：圆、文字、块和测点组装。
- `cad-laneway-plugin/core/parse.js`：DXF 路径、文字及部分曲线解析。
- `cad-laneway-plugin/core/lanes.js`：边线拼接、配对、点筛选和插值。
- `cad-laneway-plugin/tests/real-corridor-evaluation.mjs`：人工真值点建巷对拍；其他回归测试位于同一 `tests/` 目录。
- `cad-laneway-plugin/runtime/`：随包 DWG 转换运行时及许可文件，打包时需一并保留。
